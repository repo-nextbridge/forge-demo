# Your storefront

This is a complete copy of the Forge reference storefront, cut from a single Forge release. It is a normal
Next.js project: no Forge monorepo, no pnpm workspace, no path aliases pointing anywhere you cannot see. Every
dependency resolves from a registry or from the tarballs published with that release.

From here on it is **yours**.

## What you own

**Every file.** Change a template, delete a page, replace the design, rewrite the product page. Nothing in this
project is generated by us and nothing gets overwritten behind your back — because nothing here is updated by
us at all.

**The theme.** Design tokens arrive as a package (`@forgeco/theme-storefront-vanilla`), but the components
are yours to edit. The Forge convention is that components bind to semantic tokens instead of literal colors,
so a re-skin stays a `tokens.css` edit — `src/structure.test.ts` enforces that rule on your copy, and if you
decide you want the rule gone, delete the test. It is your repo.

**Your static files — in `public/assets/`.** A logo, an og-image, a favicon you own. They are served at
`/assets/<name>` and the image copies the directory for you.

> ⚠️ **The root of `public/` is not a place to put them.** This storefront routes by host: a request for
> `/logo.png` is rewritten to `/s/<store>/logo.png`, which is not a page, so the file 404s while sitting in the
> image the whole time. `assets/` is the one prefix excluded from that rewrite (`src/middleware.ts`). If you
> want a second one, add the prefix there — a prefix, not a list of filenames, which is the form that stops
> being true the first time somebody adds a file and forgets the list.
>
> A file you `import` in a component needs none of this: the bundler emits it under `/_next/static/`, which is
> already excluded and already copied.

**The extension points.** Two registries, each one import and one entry:

- `src/lib/extensions/registry.tsx` — the blocks a page can render in a slot.
- `src/lib/extensions/gate.ts` — how the `storefront:gate` slot is resolved. The slot is the kit's and this
  fork still mounts it; **nothing in this box fills it**, so it resolves to nothing and the route is served
  as-is.

Which extensions are *installed* is read from the kernel at runtime (`read.extensions`); these registries only
say what this build knows how to render. A block package installed from the registry also has to be listed in
`transpilePackages` in `next.config.mjs` — it ships as `.tsx` + CSS Modules, and your bundler compiles it.

**The tests.** The reference suite came with the copy and runs here (`npm test`): the structural rules, the
theme-token binding, the catalog and cart DOM flows. They are the reason you can make the first change and know
whether you broke anything. They are also yours to delete.

One family did not come along: files named `*.guard.test.ts`. In the Forge repository a *guard* asserts an
invariant of **that repository** — for instance that the reference storefront names none of the Forge demo's
apps. True here too, and about the wrong project. What you inherited are the tests that say something about
*your* storefront.

## What is not here: checkout, account and orders

This copy is the **storefront** — home, category and search pages, the product page, the mini-cart. It stops
where the money starts. `/checkout`, `/account`, the login, and the order pages are served by the Forge
**checkout** app, on this same host: your edge routes those paths to it and everything else to you. You do not
link to another domain and you do not proxy anything by hand — you link to `/checkout`, exactly as the pages in
this copy already do.

That is a boundary in your favour, and it costs you nothing you had:

- **You stop inheriting the checkout's maintenance.** Payment methods, tax and shipping rules, the order state
  machine, login and one-time codes, the account pages — none of it is in this repo, so none of it is yours to
  merge, patch or debug.
- **You keep receiving its evolution.** The rule in "What you give up" below is about the code you now own; the
  checkout is code you do **not** own, so a new payment brick or a faster confirmation step reaches your store
  by pinning a new `checkout` image in `forge.lock`. No merge, ever — in this direction that is the good news.
- **It still looks like your store.** The checkout renders the same chrome and the same theme, read from your
  store's data through the same port: your logo, your menu, your footer, your tokens. You do not style it by
  editing it.
- **You can still take it.** The checkout is an app of the Forge like this one, and it is forkable on the same
  terms. Nothing here forces the hosted one on you — it is simply the piece almost nobody wants to own.

**One dependency runs the other way, and it is declared rather than accidental:** the order and account pages
of the checkout show product photos, and they ask **your** storefront for them, at `/api/img/<format>/<width>/<provider_key>`
on this host. It is one of the routes listed under "What you must keep working" for exactly this reason. Delete
it or change its shape and the photos disappear from pages that are not in this repo.

## What you give up

**Our evolution of this code.** The moment you change a file here, the reference storefront and your storefront
are two different projects. Improvements we make to ours — a faster PLP, a nicer checkout step, a fix to a
component — do not reach you. There is no merge, ever. This is the same rule the kernel follows in the opposite
direction: the kernel is never forked, and the storefront is never merged.

**Nothing else.** You keep talking to the same kernel through the same door, and you keep receiving kernel
updates by pinning a new image in `forge.lock`. Owning the front costs you the front's updates, not the
platform's.

## What you must keep working

The storefront is a pure **server-side consumer of the kernel's read/command port**. It never touches a
database, and it reaches the kernel over your compose network — never from the shopper's browser. The contract
is the environment:

| Variable | What it is |
|---|---|
| `FORGE_READ_BASE_URL` | where the kernel answers `GET /v1/read/*` |
| `FORGE_COMMAND_BASE_URL` | where the kernel accepts `POST /v1/commands/*` |
| `FORGE_STORE_HOSTS` | host → store id mapping, one instance can serve several |
| `FORGE_MEDIA_BASE_URL` | base of your media bucket |
| `FORGE_REVALIDATE_SECRET` | shared secret the kernel uses to invalidate cached pages |

`@forgeco/storefront-kit`'s `config` module is the full list.

**What is NOT in it, deliberately.** The social-login keys (`FORGE_GOOGLE_*`, `FORGE_APPLE_*`) and
`FORGE_CUSTOMER_ASSERTION_PRIVATE_KEY` — the Ed25519 key that signs the customer factor assertion — belong to
the **checkout** app and are given only to it. This project never starts a login handshake: it links to
`/account/login`, which the edge routes to the checkout on the same host. Handing a signing key to the half
you are most likely to fork and self-host would widen the blast radius for a capability this half never
exercises.

Two **routes** are part of the contract as well, because something outside this project calls them:
`/api/revalidate`, which the kernel uses to invalidate cached pages, and `/api/img/<format>/<width>/<provider_key>`, the
image port — used by your own pages and, as the section above says, by the checkout app's order and account
pages. Rename or remove either and the caller has no way to know.

## Running it

```bash
npm install                       # the Forge packages come from the release tarballs; see below
npm run dev                       # http://localhost:3000
npm test                          # the suite that came with the copy
npm run typecheck
```

The `@forgeco/*` dependencies are published with each Forge release. Until you point npm at a registry
that has them, install them from the tarballs attached to the release:

```bash
npm install ./forge-packages/*.tgz
```

## Shipping it

```bash
FORGE_BUILD_STANDALONE=1 npm run build     # emits .next/standalone — a minimal server + traced deps
docker build -t <your-registry>/storefront:<tag> .
docker push <your-registry>/storefront:<tag>
```

Then point your instance at it: in `forge.lock`, replace the `images.storefront` digest with your own, and
`docker compose up -d`. Your compose file does not care whose image it is — it only cares that it answers on
port 3000 and speaks to the kernel with the variables above.

The `Dockerfile` here is thin: it copies the build you already ran and tested, instead of rebuilding inside the
container. Build first, image second.
